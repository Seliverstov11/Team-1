# Backend — Сладкий Мастер

Rust + Axum + libSQL (SQLite). На этом API строятся сайт, CRM и мобильная практика.

## Запуск

```bash
cargo run
```

Всё. БД создаётся файлом `data.db` рядом, миграции применяются сами, демо-товары заливаются при первом старте. Токены и интернет не нужны.

API поднимается на `http://localhost:8080`, проверка — `GET /health`.

Через Docker, если Rust не установлен:

```bash
docker compose up --build
```

## Переменные окружения

Все необязательные, значения по умолчанию рабочие. Образец — `.env.example`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `8080` | Порт |
| `DATABASE_PATH` | `data.db` | Файл локальной БД |
| `RUST_LOG` | `info` | Подробность логов |
| `TURSO_DATABASE_URL` | — | Turso для задеплоенного демо |
| `TURSO_AUTH_TOKEN` | — | Токен Turso |

Пока переменные Turso пустые, backend работает с локальным файлом. Как только обе заданы — уходит в Turso. Секреты в репозиторий не кладём (H12).

## Эндпоинты

Полный контракт с телами запросов и ответов — в `openapi.yaml`.

### Каталог (публичный)

| Метод | Путь |
|---|---|
| GET | `/api/catalog/categories` |
| GET | `/api/catalog/products` |
| GET | `/api/catalog/products/{id}` |

Фильтры товаров: `category_id`, `search`, `in_stock`, `limit`, `offset`.

### Заказы (менеджер)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/orders` | Список, фильтр `?status=` |
| POST | `/api/orders` | Создать, резервирует остатки |
| GET | `/api/orders/{id}` | Заказ с позициями |
| PATCH | `/api/orders/{id}` | Сменить статус |

### Склад (кладовщик)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/warehouse/stock` | Остатки с пометкой «заканчивается» |
| GET | `/api/warehouse/movements` | Журнал движений |
| POST | `/api/warehouse/movements` | Приход или корректировка |

## Как считаются остатки

```
доступно = на складе − в резерве
```

| Событие | Что происходит |
|---|---|
| Создан заказ | `резерв += количество` |
| Статус `delivered` | `склад −= количество`, `резерв −= количество` |
| Статус `cancelled` | `резерв −= количество`, склад не трогаем |

Создание заказа идёт одной транзакцией с блокировкой на запись. Если хотя бы одной позиции не хватает — не резервируется ничего, заказ не создаётся. Два одновременных заказа не уведут остаток в минус.

Приход и корректировка не дают опустить склад ниже нуля и ниже того, что уже зарезервировано под заказы.

Каждое изменение пишется в `stock_movements` — видно, кто, когда, сколько и по какому заказу.

## Деньги и количества

В SQLite нет типа для дробей без потери точности, а `float` даёт `1880.0000000002` и расхождения в суммах. Поэтому в БД всё целыми:

- `price_tiyn` — цена в тиынах. `1 880 ₸` = `188000`
- `*_milli` — количество ×1000. `2,5 кг` = `2500`

Наружу уходит строкой: `"price": "1880.00"`, `"quantity": "2.500"`. Строка, а не число, чтобы JSON-парсер на фронте не превратил это во float.

Запросы принимают тоже строку: `{"quantity": "2.5"}`.

## Схема БД

| Таблица | Что хранит |
|---|---|
| `categories` | Категории, с вложенностью |
| `products` | Товары, остаток, резерв, весовой флаг, минимум и шаг заказа, полка |
| `product_attributes` | Характеристики — произвольные пары «название — значение» |
| `employees` | Сотрудники: админ, менеджер, кладовщик |
| `clients` | Клиенты |
| `orders` | Заказы и статусы |
| `order_items` | Состав заказа |
| `stock_movements` | Журнал движений склада |

Удаления товаров нет — есть `is_archived`. Иначе развалилась бы история заказов, а у заказчика в таблице полно позиций, которые уже не продаются, но «удалять никто не станет».

### Характеристики

Не колонки, а строки в `product_attributes`. Заказчик прямо просил динамические: общие для всех только цвет, вес и материал, остальное своё у каждой категории, и при добавлении товара можно придумать новую характеристику. Фиксированный набор полей это требование не покрывает.

### Минимум и шаг заказа

Весовой товар продаётся не фиксированными фасовками, а от минимума с шагом: шоколад от 500 г по 100 г. Поля `min_order_milli` и `order_step_milli`, проверяются при создании заказа. Для штучного товара по умолчанию одна единица.

### Полка

Сканера штрихкодов у заказчика нет, товар ищут по полке. Полка хранится на товаре и записывается в движение при приёмке.

В `order_items` название и цена сохраняются снимком на момент заказа. Поднимем цену — старый заказ не изменится.

## Статусы заказа

```
new → confirmed → assembling → ready → delivered
                                    ↘ cancelled
```

Какие переходы разрешены и когда именно списывается товар — пока наше предложение, с заказчиком не согласовано. См. открытые вопросы в #8.

```
└── Dockerfile
```
