# Backend — Сладкий Мастер

Rust + Axum + libSQL (SQLite). На этом API строятся сайт, CRM и мобильная практика.

## Запуск

```bash
cargo run
```

Всё. БД создаётся файлом `data.db` рядом, миграции применяются сами, демо-товары заливаются при первом старте. Токены и интернет не нужны.

API поднимается на `http://localhost:8080`, проверка — `GET /health`.

Через Docker, если Rust не установлен:

```bash
docker compose up --build
```

## Переменные окружения

Все необязательные, значения по умолчанию рабочие. Образец — `.env.example`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `8080` | Порт |
| `DATABASE_PATH` | `data.db` | Файл локальной БД |
| `RUST_LOG` | `info` | Подробность логов |
| `TURSO_DATABASE_URL` | — | Turso для задеплоенного демо |
| `TURSO_AUTH_TOKEN` | — | Токен Turso |

Пока переменные Turso пустые, backend работает с локальным файлом. Как только обе заданы — уходит в Turso. Секреты в репозиторий не кладём (H12).

## Эндпоинты

Полный контракт с телами запросов и ответов — в `openapi.yaml`.

### Каталог (публичный)

| Метод | Путь |
|---|---|
| GET | `/api/catalog/categories` |
| GET | `/api/catalog/products` |
| GET | `/api/catalog/products/{id}` |

Фильтры товаров: `category_id`, `search`, `in_stock`, `limit`, `offset`.

### Заказы (менеджер)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/orders` | Список, фильтр `?status=` |
| POST | `/api/orders` | Создать, резервирует остатки |
| GET | `/api/orders/{id}` | Заказ с позициями |
| PATCH | `/api/orders/{id}` | Сменить статус |

### Склад (кладовщик)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/warehouse/stock` | Остатки с пометкой «заканчивается» |
| GET | `/api/warehouse/movements` | Журнал движений |
| POST | `/api/warehouse/movements` | Приход или корректировка |

## Как считаются остатки

```
доступно = на складе − в резерве
```

| Событие | Что происходит |
|---|---|
| Создан заказ | `резерв += количество` |
| Статус `delivered` | `склад −= количество`, `резерв −= количество` |
| Статус `cancelled` | `резерв −= количество`, склад не трогаем |

Создание заказа идёт одной транзакцией с блокировкой на запись. Если хотя бы одной позиции не хватает — не резервируется ничего, заказ не создаётся. Два одновременных заказа не уведут остаток в минус.

Приход и корректировка не дают опустить склад ниже нуля и ниже того, что уже зарезервировано под заказы.

Каждое изменение пишется в `stock_movements` — видно, кто, когда, сколько и по какому заказу.

## Деньги и количества

В SQLite нет типа для дробей без потери точности, а `float` даёт `1880.0000000002` и расхождения в суммах. Поэтому в БД всё целыми:

- `price_tiyn` — цена в тиынах. `1 880 ₸` = `188000`
- `*_milli` — количество ×1000. `2,5 кг` = `2500`

Наружу уходит строкой: `"price": "1880.00"`, `"quantity": "2.500"`. Строка, а не число, чтобы JSON-парсер на фронте не превратил это во float.

Запросы принимают тоже строку: `{"quantity": "2.5"}`.

## Схема БД

| Таблица | Что хранит |
|---|---|
| `categories` | Категории, с вложенностью |
| `products` | Товары, остаток, резерв, весовой флаг, минимум и шаг заказа, полка, вариант и группа, опт |
| `product_attributes` | Характеристики — произвольные пары «название — значение» |
| `employees` | Сотрудники: админ, менеджер, кладовщик |
| `clients` | Клиенты, тип и город |
| `client_prices` | Персональные цены: клиент видит свою цену вместо общей |
| `orders` | Заказы и статусы |
| `order_items` | Состав заказа |
| `stock_movements` | Журнал движений склада |

Удаления товаров нет — есть `is_archived`. Иначе развалилась бы история заказов, а у заказчика в таблице полно позиций, которые уже не продаются, но «удалять никто не станет».

### Характеристики

Не колонки, а строки в `product_attributes`. Заказчик прямо просил динамические: общие для всех только цвет, вес и материал, остальное своё у каждой категории, и при добавлении товара можно придумать новую характеристику. Фиксированный набор полей это требование не покрывает.

### Минимум и шаг заказа

Весовой товар продаётся не фиксированными фасовками, а от минимума с шагом: шоколад от 500 г по 100 г. Поля `min_order_milli` и `order_step_milli`, проверяются при создании заказа. Для штучного товара по умолчанию одна единица.

### Варианты товара

В таблице заказчика один товар — это несколько строк с общим «ID товара»: шоколад 54 % идёт как 100 г, 500 г и 1 кг, у каждой фасовки своя цена и свой остаток. Отдельной таблицы вариантов нет: строка `products` остаётся единицей продажи, а `group_id` склеивает их в одну карточку. Фронт запрашивает `/api/catalog/products?group_id=...` и рисует переключатель.

### Три цены

`price_tiyn` — розница, `wholesale_price_tiyn` — опт от `wholesale_min_qty` единиц, `client_prices` — персональная цена конкретного клиента. Это не скидки и не промокоды, которых заказчик не захотел, а разные прайсы.

Выбор цены в `src/pricing.rs`, порядок такой:

1. персональная цена, если заведена;
2. иначе опт, если количество дотянуло до порога;
3. иначе розница.

Считает цену бэкенд, а не фронт: цену заказа определяет тот, кто отвечает за деньги. В строке заказа остаётся `price_kind` — `retail`, `wholesale` или `personal`, видно, почему вышла такая сумма.

Каталог отдаёт персональную цену отдельным полем: `GET /api/catalog/products?client_id=...` вернёт `personal_price` рядом с розничной. Авторизации пока нет, поэтому клиент передаётся параметром — когда появятся учётные записи, он будет браться из сессии, а параметр уйдёт.

**Открытый вопрос заказчику:** что делать, если персональная цена выше оптовой. Сейчас персональная выигрывает — она договорная, и подменять её молча хуже. Нужно подтвердить.

### Оплата

Онлайн-оплаты не будет: заказчик отказался от интеграции, остаются наличные и статический QR Kaspi. Система о поступлении денег не узнаёт, поэтому факт оплаты проставляет менеджер — `POST /api/orders/{id}/payment`. Попытка создать заказ с `payment_method: online` отбивается.

Возврат принимается только по оплаченному заказу, сумма больше итога — тоже отбивается.

### Полка

Сканера штрихкодов у заказчика нет, товар ищут по полке. Полка хранится на товаре и записывается в движение при приёмке.

В `order_items` название и цена сохраняются снимком на момент заказа. Поднимем цену — старый заказ не изменится.

## Статусы заказа

```
new → confirmed → assembled → handed_over → shipped → delivered → completed
                                                              ↘ cancelled
```

Восемь статусов — ровно те, что встречаются в таблице заказчика.

Резерв ставится при создании заказа. Списание — на `handed_over` и дальше: по условиям магазина товар уходит «при выдаче или передаче в доставку», а не в момент, когда клиент его получил. Повторно не списывается, признак — запись `out` в `stock_movements`. Отмена возвращает резерв, если списания ещё не было.

## Данные заказчика

В базе лежит не демо-набор, а боевой каталог из файла «Сладкий_мастер_данные_для_разработки_1.xlsx», переданного 12.11.2026: 23 категории, 289 позиций, 1445 характеристик, 22 клиента и 24 примера заказов. Демо-строки из миграции 002 удаляются миграцией 005 — у фронта и бэка должен быть один набор данных.

Правки вносятся в таблицу заказчика и перегенерируются, а не правятся руками в SQL:

```bash
python3 tools/xlsx2tsv.py «путь к таблице.xlsx» > /tmp/table.tsv
python3 tools/gen_seed.py /tmp/table.tsv > migrations/005_catalog_from_customer.sql
```

Чего в данных не оказалось: весовых товаров нет совсем — всё продаётся штуками, упаковками, наборами и рулонами, поэтому минимум и шаг заказа пока везде равны единице. Фотографий тоже нет, заказчик их не передал: в таблице указано только имя будущего файла, оно лежит в `image_name`, а подбор фото за командой.

## Тесты

```bash
cargo test
```

Покрыт пересчёт денег и количеств — там, где легче всего потерять копейку.

Проверены на запущенном сервере: розница до порога опта, опт ровно на границе, персональная цена поверх обеих, обязательные телефон и адрес доставки, отказ онлайн-оплаты, возврат без оплаты, переплата, оплата целиком.

Суммы сида сверены с таблицей заказчика: сумма строк равна шапке заказа во всех 24 заказах, итог равен товарам плюс доставка, цена × количество равно сумме строки. Расхождений нет.
