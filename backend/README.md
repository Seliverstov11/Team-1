# Backend — BAKELOOM

Rust + Axum + libSQL (SQLite). Один API для сайта, CRM и будущей мобильной практики (H7).
Требования — ТЗ BAKELOOM v1.0 от 15.11.2026, в коде и контракте указаны номера пунктов.
Полный контракт с телами запросов и ответов — [`openapi.yaml`](openapi.yaml).

## Запуск

```bash
cp .env.example .env
cargo run
```

БД создаётся файлом `data.db` рядом, миграции и демо-данные применяются сами. Интернет и токены не нужны.
API — `http://localhost:8080`, проверка — `GET /health`.

Через Docker, если Rust не установлен:

```bash
cp .env.example .env
docker compose up --build
```

Тесты:

```bash
cargo test
```

### Демо-входы

Пароль у всех — из `BOOTSTRAP_PASSWORD` в `.env` (в образце `bakeloom-demo`). Он выставляется при старте сотрудникам, у которых пароля ещё нет; дальше владелец меняет пароли через `PATCH /api/employees/{id}`.

| Логин | Роль | Что может |
|---|---|---|
| `owner` | владелец (`admin`) | всё: каталог, цены, персональные цены, сотрудники, аналитика |
| `dana`, `aliya` | менеджер | заказы, клиенты, оплаты, дашборд |
| `sklad` | кладовщик | склад, приход, сборка, выдача; оплаты не видит |

```bash
curl -s localhost:8080/api/auth/login -H 'content-type: application/json' \
  -d '{"login":"owner","password":"bakeloom-demo"}'
# → {"token":"…"}; дальше заголовок Authorization: Bearer <token>
```

Покупатель регистрируется сам: `POST /api/auth/client/register` с именем, телефоном и паролем.

## Жизненный цикл заказа

```
new → confirmed → assembled → handed_over → shipped → delivered → completed
   ↘ cancelled  ↘ cancelled  ↘ cancelled      ↘ completed (самовывоз)
```

Переходы только по стрелкам (ФТ-З-03), перескочить нельзя — 409.

| Шаг | Кто | Что происходит |
|---|---|---|
| Оформление | сайт, менеджер | резерв всех позиций одной транзакцией; не хватает хоть одной — не меняется ничего. Заказ привязывается к клиенту по телефону, уходит уведомление в Telegram |
| `confirmed` | менеджер | заказ попадает в очередь сборки |
| Сборка | кладовщик | галочка у каждой позиции; нехватка (`short_qty`) делает заказ проблемным |
| Правка состава | менеджер | в статусах `new` и `confirmed`: количество, скидка, добавить, убрать. Резерв пересчитывается, проблема по нехватке снимается сама |
| `assembled` | кладовщик | не пройдёт, пока есть нехватка или проблема |
| `handed_over` | кладовщик | списание товара и резерва; для доставки нужен адрес, «Уточнить у клиента» не годится (ФТ-О-06) |
| `cancelled` | менеджер | только до передачи; оплаченный заказ — сначала возврат (ФТ-П-05). Резерв возвращается |

Каждое действие пишется в журнал заказа (`GET /api/orders/{id}/events`): кто, когда, что изменил.

### Оплата

Онлайн-оплаты нет: статический QR Kaspi и наличные (ФТ-П-01). Система о платеже не узнаёт, отметку ставит менеджер — `POST /api/orders/{id}/payment`:

| `payment_status` | Когда |
|---|---|
| `paid` | вся сумма |
| `partial` | предоплата, `paid` меньше итога |
| `unpaid` | снять ошибочную отметку |
| `refunded` | возврат по оплаченному заказу |

Поступления за период дашборд считает по этим отметкам, возвраты вычитаются.

## Цены

В строке заказа цена сохраняется снимком: изменение каталога старые заказы не трогает (ФТ-Ц-05). Цену считает сервер, а не сайт. Порядок в `src/pricing.rs`:

1. персональная цена клиента, если заведена;
2. опт, если включён `WHOLESALE_ENABLED` и количество дотянуло до порога;
3. общая цена.

Персональную цену видит только вошедший покупатель или сотрудник, который смотрит каталог за клиента (`?client_id=`). Гостю параметр ничего не даёт — иначе чужие договорные цены были бы видны всем. Клиент с персональными ценами не может зарегистрироваться сам: подтвердить телефон без SMS нечем, пароль ему выдаёт владелец.

## Деньги и количества

В БД всё целыми: `*_tiyn` — тиыны (1 880 ₸ = 188000), `*_milli` — количество ×1000 (2,5 кг = 2500). Наружу и внутрь — строкой: `"price": "1880.00"`, `"quantity": "2.5"`, чтобы JSON-парсер не превратил это во float.

## Вход

После 5 неверных паролей подряд по одному логину или телефону — пауза 5 минут, ответ 429.

## Схема БД

| Таблица | Что хранит |
|---|---|
| `categories` | Категории с вложенностью |
| `products` | Товары: остаток, резерв, минимум остатка, минимум и шаг заказа, полка, фасовка и группа |
| `product_attributes` | Характеристики — у каждого товара свои пары «название — значение» |
| `employees` | Сотрудники: роль, логин, хеш пароля |
| `clients` | Клиенты: телефон, тип, город, учётная запись |
| `client_prices` | Персональные цены |
| `sessions` | Входы; хранится только хеш токена |
| `orders` | Заказы: статус, оплата, доставка, «срочный», «проблемный» |
| `order_items` | Состав со снимком цены, отметки сборки и нехватки |
| `order_events` | Журнал действий по заказу |
| `stock_movements` | Журнал движений склада |
| `visits` | Посещения сайта для аналитики: устройство, браузер, система, без IP |

## Демо-данные

Из таблицы заказчика от 12.11.2026, по 5 карточек на категорию: заказчик просил не переносить весь каталог — часть позиций устарела, наполнение он сделает сам (В3 28:37). В первую очередь взяты товары из примеров заказов. Итого 23 категории, 98 карточек (124 строки с фасовками), 22 клиента, 24 заказа.

Правки — в таблицу заказчика и перегенерация, а не руками в SQL:

```bash
python3 tools/xlsx2tsv.py «таблица.xlsx» > /tmp/table.tsv
python3 tools/gen_seed.py /tmp/table.tsv --per-category 5 > migrations/007_seed_sample.sql
```

Миграция 007 перезаливает демо-данные: на старой локальной БД тестовые заказы пропадут. Если нужна чистая база — удалите `data.db`.

## Известные ограничения

- Регистрация покупателя без подтверждения по SMS. Поэтому клиентам с персональными ценами пароль выдаёт владелец.
- Накладная сделана по стандартной форме З-2; поля сверим с образцом, который обещал заказчик.
- Сколько товара не хватило при сборке, кладовщик отмечает в заказе, а складской остаток правит отдельной корректировкой с причиной.
